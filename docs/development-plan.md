# Development plan — Revision 6.1 build sequence

**Status:** locked before Phase 0. Agreed in the planning session that produced Revision 6.1; recorded here so the sequence lives in the repository, not in chat.
**Authority:** this document orders the work. It does not define product behaviour or architecture. Requirements are `spec.md` (§31 acceptance criteria, §32 guardrails), the locked stack is `technology-decisions.md`, renderer and model contracts are `event-renderer-system.md` and `model-contracts.md`. When this plan and those documents disagree, they win and this plan is corrected.
**How work is routed:** `CLAUDE.md §11` (task packets, Haiku → Sonnet → Opus → Fable, one integrated review per meaningful change).

## Principles behind the order

1. **Deterministic core before live AI.** The canonical pipeline requires a `CompositionTree` to pass deterministic compilation and rendered-geometry verification through the production renderer before a `ResolvedDesignSpec` is final. So the compiler/renderer engine (Phase 3) precedes AI orchestration (Phase 4). The engine needs no auth, database or model call, and it already has 46 adversarial fixtures and 72 frozen confirmation trees waiting for it (`../proof-b/`).
2. **Settle the one open runtime question first.** Geometry verification runs headless Chromium against the production renderer before a spec is persisted. The approved options were a Vercel Node runtime with a serverless Chromium build, or a small render worker (settled by the Phase 0 spike verdict in `technology-decisions.md`, "Geometry verification runtime": Vercel serverless Chromium). Client-side verification in the host's browser is **not** an interchangeable fallback; it would change an architectural invariant and requires a deliberate revision.
3. **Incremental physical schema, complete conceptual model.** Migrations arrive with their domain phase, but the whole domain model (`spec.md §24`) and stable identifiers and RLS boundaries are understood before Phase 1 so later domains do not collide with early assumptions.
4. **Spend controls ship with the first production model call**, not in hardening. The proof hit an organisation spend ceiling mid-run. Requirements: one batch in flight per event, per-event and per-account daily caps, global ceiling and alerts, rate limits, idempotency, usage telemetry (`spec.md` generation and spend limits).
5. **Human design-quality review runs twice.** Once now on the Phase B sheets for baseline and calibration against the hand-authored library; again on the frozen production generation stack as the launch gate (`CHANGELOG-v6.md`, open condition 2). The first run informs the production prompt and model; it does not close the launch gate.
6. **Stable collaborator anchors are contractual.** The production renderer exposes semantic section identifiers (hero, details, rsvp, registry, …) from its first port so Creation Mode controls attach to slots, never to inferred DOM shape.
7. **Capabilities, ContentProfile and FeaturePresentationState are pure derivation functions from the start**, fed sparse data in early phases. Never hardcoded defaults. Semantics are settled in `spec.md §0b` and §11.4: capabilities = enabled features; content profile = present content; presentation state = guest visibility.
8. **Required details are captured early, during generation**, as publish requirements with bounded provisional content and deterministic re-fit (`spec.md §7.3`, §0b). Phase 2 owns the minimal flow so Phase 4 never builds a throwaway onboarding UI.

## Recorded deviations

- **`spec.md §31 — Prompt, auth, and generation`: "Required details are collected only when missing and while generation runs, and never block concepts from appearing."** Phase 2 satisfies every part of this except "while generation runs", which it cannot: generation is Phase 4 and the AI provider is deliberately unimplemented until then. Phase 2 collects the details anyway, exactly as the criterion intends, and the generation surface states plainly that no design has been generated yet rather than narrating work that is not happening. The bullet is checkable once Phase 4 lands; until then it is knowingly partial, not met. Recorded here so no later reader mistakes the Phase 2 screen's honesty for a regression, and so nobody papers over it with copy that implies generation is running.

## Decisions that must not be reopened by this plan

- The Phase 3/4 order (engine before AI) and the Phase 0 spike as a go/no-go.
- Client-side geometry verification is rejected as a casual fallback.
- Capability semantics and early required-details capture are settled in Revision 6.1; implementation follows `spec.md §0b`, not this document.
- The locked stack in `technology-decisions.md`.
